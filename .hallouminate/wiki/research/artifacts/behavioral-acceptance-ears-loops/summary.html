Choose checks by failure risk

Do not generate every check for every task. Keep the smallest set that covers distinct risks.

A requirement is not yet a test

EARS distinguishes events, states, unwanted behavior, optional features, and always-active requirements. Gherkin describes context, action, and expected outcome.

Illustrative EARS requirement

When an experiment exports a patch, the patch shall reproduce the evaluated candidate on its declared base.

The fixture below has a separate contract: doubling 7 produces 14. This is an example, not an existing Skillz command.

Given a clean checkout at base B
And "./fixture double 7" incorrectly prints "7"
When I apply the exported patch
And I run "./fixture double 7"
Then the exit status is 0
And stdout is exactly "14"

Evaluator control: the same acceptance check must reject a no-op patch on base B.

This checks the exporter on a fixture. It does not establish that a real target skill improves.

Small acceptance record
  • Requirement ID and one required response.
  • Concrete normal and failure examples.
  • Actual entrypoint and boundaries that remain real.
  • Observable result and independent expected value.
  • False-success case and executable check.
  • Deadline when the requirement depends on time.

For “while” requirements, test relevant transitions—not one snapshot. Keep existing test tooling when it can execute the examples.

Evidence: Original EARS paper; Gherkin reference. The mapping and fixture are authored examples.

Use different end conditions

Acceptance repair

Question: Does the required behavior work?

  1. Run a fixed real-path check.
  2. Diagnose one observed failure.
  3. Make a coherent correction.
  4. Re-run acceptance and regression checks.

Stop: acceptance and required gates pass, the budget expires, or progress needs a decision.

Optimization hill climb

Question: Can an accepted system improve one objective?

  1. Start from an accepted baseline.
  2. Keep behavior and architecture constraints fixed.
  3. Compare one candidate under matched conditions.
  4. Retain only a justified gain.

Stop: the agreed target, budget, no-progress rule, or decision boundary.

A retry scheduler is neither. Repeating the same attempt can produce one success without improving first-attempt reliability.

Use strict ratchets for deterministic costs. Use repeated trials and an uncertainty policy for noisy agent quality.

Keep final validation tasks separate from iteration tasks. Repeatedly consulting a holdout turns it into development evidence.

Local mismatch: your installed hill-climb skill explicitly continues after reaching its target. Do not reuse that stopping rule for acceptance work.

Evidence: Evaluator-optimizer patterns; Adaptive holdout reuse. The two procedures are proposed adaptations.

Optimize behavior without rewarding tangled code

Candidate rule: retain a gain only when behavior, architecture, security, and relevant regression checks also pass.

A higher score must not compensate for a failed hard constraint.

Admit useful tests

Ask: “Which distinct failure does this test reject?”

  • Keep fast tests for meaningful decisions and boundaries.
  • Parameterize repeated examples.
  • Use properties for invariants and sequences for state transitions.
  • Challenge assertions with a relevant seeded defect.

Do not optimize test count, coverage, or mutation score alone.

Protect code structure

  • Check forbidden imports and dependency cycles.
  • Keep state-transition ownership clear.
  • Require a demonstrated need for abstractions.
  • Remove superseded paths and duplicate state.
  • Re-run unchanged behavior checks after refactoring.

Complexity and line counts are review signals, not definitions of quality.

Warning signs: private renames break many tests; fixtures copy the implementation; snapshots update automatically; the suite grows but the live complaint remains.

Keep overlapping tests when they cover different risks. Do not remove guards without approval.

Evidence: Mutation-testing limits; Stateful testing; Executable architecture checks. The retention rule is engineering synthesis, not a proven guarantee.
